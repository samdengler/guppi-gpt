GuppiGPT decision log

How the single page chat design reached its current shape: the revisions, the alternatives set aside, and the answers given in review.

This log is a companion to the design document. The design document describes the system as it stands; this log records what changed on the way there and why, so the design can be read without that history. Entries are in the order they happened.

2. Decisions that were reversed

Each entry records the earlier choice, what replaced it, and the reason. The current alternative is stated in the design document's decisions table; this section exists so the earlier choice is not proposed again without knowing why it was set aside.

Runtime bound to the edge gateway

Revision 3 set allowedWorkloadConfiguration on the runtime JWT authorizer so that a token presented directly to the runtime endpoint would be refused. Revision 8 turned it off after the first deploy. A runtime with the binding demands a transaction token from the gateway, and the gateway supplies one only when it signs the outbound request with its own role; a JWT runtime rejects that signed request as an authorization method mismatch, and token passthrough forwards the user token without any transaction token. The binding comes back, through the bind_runtime_to_gateway context flag, once the gateway stamps passthrough requests or the runtime accepts a signed request that carries the user token.

Origin header secret as a deploy-time parameter

Revision 5 described the CloudFront-only WAF rule as matching a secret header, and the repository rule for secrets was that every one is a CloudFormation parameter supplied by the deploy script from 1Password. Revision 10 instead has the stack generate the value in Secrets Manager and reference it from the CloudFront origin header and the WAF rule as a {{resolve:secretsmanager}} dynamic reference. Nobody needs to know the value, a deploy with 1Password locked still works, and the value never appears in the template. The parameter route stays for the Google OAuth client, which is a value the stack cannot produce.

Bundled client libraries

Revisions 2 to 7 planned oidc-client-ts for PKCE and @ag-ui/client for the stream, bundled by one esbuild step. Revision 10 dropped both: the PKCE flow and the SSE reader are about forty lines each, and the page needed no other tooling. Revision 12 brought @ag-ui/client and the esbuild step back on request, for the event typing, ordering checks, and abort handling; the hand-written reader is the recorded fallback. oidc-client-ts stays out, since the PKCE flow is forty lines and works.

Nothing saved in the browser

Revisions 1 to 12 held that no message is persisted anywhere, and the page said so in its hint. Revision 13 keeps that as the default and adds browser-only history behind the history flag, with the hint changing to say chats are saved on this device only when it is on. The server-side rule is unchanged; conversation logging to S3 is a separate proposal awaiting decisions on anonymity and retention.

Lambda as the compute

Revision 1 used a Lambda Function URL with response streaming as the only compute: it validated nothing (there was no auth), called ConverseStream, and relayed deltas as NDJSON. It was replaced in revision 2 by AgentCore Runtime because the runtime validates JWTs, streams SSE, isolates sessions, and speaks AG-UI as configuration, and because a Lambda has no natural place for an MCP client with a long-lived session. The design document keeps a short statement of the conditions under which a Lambda would come back.

Private NDJSON wire format

Revision 1 defined a three-event NDJSON stream (delta, done, error) over a fetch POST. Revision 2 replaced it with AG-UI after a survey of open standards: AG-UI is spoken natively by AgentCore Runtime and has a maintained Strands adapter, so neither side needs framing code. The survey also covered the Vercel AI SDK UI message stream (SSE, usable from any backend, but its value is the React useChat hook), OpenAI Chat Completions and Responses streaming (the right layer for a model proxy such as LiteLLM, but with no event for a server-side tool call), and assistant-ui and CopilotKit as component libraries. That comparison survives in the design document because it justifies the current choice.

CloudFront straight to the runtime, WAF on CloudFront

Revision 2 pointed the CloudFront /api/* behavior at the runtime's invocation endpoint using the AgentCore custom domain pattern, with a WAF web ACL on the distribution. Revision 3 inserted the edge gateway because it adds per-user rate limits keyed on the JWT, a second token check, and a place for tool or claim policy without touching the agent, and because WAF associates directly with a gateway as a regional web ACL. CloudFront kept the shared domain and nothing else.

Source reference chips and Markdown rendering

Revision 2 showed numbered source chips under each reply, fed by a CUSTOM sources AG-UI event that a tool-result hook in the agent emitted, and rendered replies as Markdown through a small parser and a whitelist sanitizer. Revision 4 removed both on review: the chips were not wanted, and plain text removed about a hundred lines of code and the only script injection surface the page had. The requirements, wire format, agent, and frontend sections were rewritten accordingly. A sentence in the problem statement that still described replies showing where material came from was corrected in revision 5.

CloudFront default hostname

Revision 4 chose the distribution's default cloudfront.net hostname and a Cognito prefix domain to avoid a certificate and DNS. Revision 5 replaced that with chat.dengler.io and auth.dengler.io once the domain was offered, at the cost of two certificates in us-east-1 and three DNS records, all created by the stack.

Rate rule keyed on source address

Revisions 3 and 4 described the WAF rate-based rule as keyed on the requesting address. Revision 5 corrected this: with CloudFront in front of the edge gateway, the gateway's WAF sees CloudFront edge addresses, so the rule keys on the viewer address in X-Forwarded-For, and a preceding rule that requires a CloudFront-set secret header makes that header trustworthy.

Direct retrieval from the runtime

Considered in revision 3 rather than chosen: the agent can call bedrock:Retrieve directly with its execution role and the Strands retrieve tool. The gateway hop was kept because it is the only place a retrieval carries the user's identity, which is what adding a second audience to the knowledge base would need. The comparison table stays in the design document.

3. Review answers, revision 4

Revision 3 closed with ten open questions. The answers, given in one review, and what each did to the design:

  1. CloudFront origin timeout against a streaming origin. Confirmed against the CloudFront origin settings reference: the timeout bounds time to first byte and the gap between packets, not total length. Consequence: RUN_STARTED before the model call, an SSE comment keepalive every 15 seconds during tool calls, and the timeout set to 60 seconds with no quota increase.
  2. Model. Claude Haiku.
  3. Retrieval tool. Retrieve, because the user-facing stream is the agent's own text and Retrieve has the shortest silent gap. AgenticRetrieveStream streams toward the agent over MCP (trace events as notifications/message, answer chunks as responseEvent), and forwarding those to the page would be app code carrying a second model's prose. It remains on the gateway for a possible multi-step mode.
  4. Admission. Any Google account. No allow-list, no pre-sign-up trigger; the edge gateway's per-user rate limits are the spend control.
  5. Bearer token. The Cognito access token at every hop, since both authorizers match allowedClients against its client_id claim.
  6. WAF threshold. Sixty requests per five minutes per viewer address, COUNT mode first.
  7. Rendering. Plain text with newlines preserved.
  8. Domain. CloudFront default hostname at the time; superseded in revision 5.
  9. One gateway or two. Two, kept separate: different audiences, different rate-limit shapes, and only the edge carries a WAF policy.
  10. Edge gateway idle handling on long streams. Low priority; covered by the keepalive in practice.

4. Naming

The name refers to GUPPI, the ship AI in Dennis E. Taylor's We Are Legion (We Are Bob), whose avatar is the Mon Calamari admiral from Star Wars. Backronyms on the G in GPT were offered and declined. The intended arc is the one Bob followed: begin with a literal, brief assistant that remembers nothing it was not handed, and add memory and a voice in later revisions. The stateless design is a starting point by intent.
